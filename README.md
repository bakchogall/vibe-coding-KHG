## 1. 이 과제가 측정하려는 것

이 과제의 목표는 **"잘 돌아가는 앱을 만드는 것"이 아닙니다.**

> **내 의도와 AI 출력 사이의 간극이 어디서 생기고, 그것을 어떻게 통제하는가.**
 
### 이 과제가 다루는 것 / 다루지 않는 것
 
단기간 로컬 웹앱으로는 상용 서비스의 확장성이나 보안을 제대로 다룰 수 없습니다. 그건 이 과제의 범위가 **아닙니다.** 대신 아래 세 가지는 프로젝트 규모와 거의 무관하게 나타나며, 이것이 평가 대상입니다.
 
| 다루는 것 | 다루지 않는 것 |
|---|---|
| 애매한 요구사항에 AI가 채워 넣는 **암묵적 가정** | 대규모 트래픽, 인프라 설계 |
| 요구사항이 바뀔 때 드러나는 **초기 설계의 취약성** | 프로덕션 보안, 인증/권한 |
| AI 출력을 **언제 받아들이고 언제 개입할지에 대한 판단** | 팀 협업 프로세스, 코드 리뷰 문화 |
 
### 중요한 오해 방지
 
**실패를 많이 겪은 사람이 유리한 과제가 아닙니다.** 평가 대상은 실패의 개수가 아니라 **판단의 질**입니다.
 
성찰기에 기록하는 것은 "문제 사례"가 아니라 **의사결정 지점**입니다. AI 출력을 그대로 받아들일지, 개입할지 판단해야 했던 모든 순간이 해당됩니다. **개입하지 않기로 한 판단도 똑같이 유효한 사례입니다.** "여기는 AI에게 맡겨도 된다고 보고 넘어갔고, 결과적으로 맞았다/틀렸다"는 기록은 개입 사례만큼의 가치가 있습니다.
 
실제로 이 과제에서 가장 배우기 어려운 것은 **어디까지 믿어도 되는지에 대한 감각**입니다.

## 2. 프로젝트 범위 제약 (하드 제약)

협상 불가 조건입니다. 위반 시 감점됩니다.

### 반드시 지킬 것

1. **브라우저에서 바로 실행되는 정적 웹**일 것 (GitHub Pages로 열려야 함)
2. **백엔드 서버를 직접 구현하지 않을 것** — 저장은 `localStorage`, `IndexedDB`, 파일 import/export만
3. **핵심 기능 1개, 화면 3개 이하**

### 금지 항목 (기타 범위가 폭발하는 것들은 예상해서 자제)

- 회원가입 / 로그인 / 사용자 계정
- 결제, 실시간 채팅, 다중 사용자 동시 편집
- 추천 알고리즘, 자체 학습 모델
- 서버 사이드 크롤링, 자체 DB 구축
- 네이티브 앱(iOS/Android), 데스크톱 앱

### 조건부 허용

- **외부 API**: 인증 키가 필요 없는 공개 API는 자유롭게 사용
- **키가 필요한 API / LLM API**: 사용자가 화면에서 자기 키를 입력하고 로컬에 저장하는 방식만 허용
- **키를 저장소에 커밋하면 감점입니다.** 이 저장소는 Public이므로 실제 유출입니다. 만약 커밋했다면 **즉시 해당 키를 폐기·재발급**한 뒤, 그 사건을 성찰기에 기록하세요.
- "AI를 붙였다"는 사실 자체는 가산점이 아닙니다.

## 3. 주제 고르기

### 주제 조건

- **최근 2주 안에 본인이 실제로 겪은 불편**에서 출발할 것
- 대학생활 또는 일상생활의 작은 문제일 것
- 아래 한 문장 규칙을 통과할 것

### 한 문장 규칙

> **[누가]** 가 **[어떤 상황]** 에서 **[무엇]** 을 **[어떻게]** 할 수 있게 한다.
> 기존에는 **[무엇으로 해결했고, 왜 불편했는지]**.

- 한 문장으로 안 써지면 **주제가 너무 큽니다.** 쪼개세요.
- 뒷문장이 안 채워지면 **주제가 너무 뻔합니다.** 각도를 바꾸세요.

### 판정 예시

| 주제 | 판정 | 이유 |
|---|---|---|
| 학교 커뮤니티 앱 | ❌ 너무 큼 | 기능 다수, 다중 사용자 필요 |
| 일정 관리 앱 | ❌ 너무 뻔함 | 기존 앱 대비 차별점 없음 |
| 계산기 | ❌ 너무 작음 | 해결하는 불편이 없음 |
| 시간표 이미지를 붙여넣으면 공강 시간을 색으로 보여주는 뷰어 | ✅ | 범위 명확, 불편 구체적 |
| 영수증을 붙여넣으면 이번 달 카테고리별 지출을 보여주는 로컬 가계부 | ✅ | 핵심 기능 1개, 로컬 저장으로 충분 |
| 과제 마감일을 넣으면 남은 시간을 압박감 있게 시각화하는 대시보드 | ✅ | 작지만 차별점 있음 |

### 참고용 주제 씨앗

그대로 쓰지 말고 본인 경험으로 변형하세요.

- 조별과제 역할을 선호도 기반으로 분배해주는 도구
- 강의계획서 텍스트를 붙여넣으면 평가 비중을 차트로 보여주는 뷰어
- 여러 명의 가능한 시간대를 받아 겹치는 구간을 찾아주는 페이지
- 자취방 냉장고 재고를 유통기한 순으로 정렬해주는 관리 페이지
- 통학 경로별 소요시간을 기록해 요일·시간대 패턴을 보여주는 로그
- 읽어야 할 PDF 논문 목록을 진척률과 함께 관리하는 트래커
- 운동 세트 기록을 최소 탭 수로 입력하게 만든 기록기

## 4. 진행 절차

**Github에서 전 과정 push 및 취합하려 했으나, 최종 결과물만 Git Pages에서 실행되면 됨, 성찰기도 자유 형식**

### Phase 0 — 나이브 베이스라인 (필수)

**생략할 수 없습니다. 이 과제에서 중요한 단계입니다.**

1. 아무 준비 없이 Claude Code에 **한 줄짜리 대충 요구사항**을 던지세요.
   예: `대학생용 시간표 앱 만들어줘`
2. 세부 지시나 수정 없이 **3~5턴만** 진행합니다.
3. 관찰 결과를 기록합니다 (다음 항목들은 예시입니다)
   - 요청하지 않았는데 AI가 **임의로 결정한 것** (스택, 데이터 구조, 화면 구성, 색상 등)
   - 동작한다고 했지만 **실제로는 안 되는 것**
   - 내가 원했던 것과 **다르게 만들어진 것**


### Phase 1 — 요구사항, 스펙 등 작성

- `CLAUDE.md`를 채웁니다. AI에게 초안을 시켜도 되지만 **반드시 읽고 고쳐야 합니다.**
- spec, plan 등 역할별 파일이나 디렉토리 구성 등 알려진 Tip 들이 널리 공유되어있지만 옵션이고 처음부터 경험해보는 것도 좋습니다. 

### Phase 2 — 재구축

Phase 0 결과물은 참고만 하고 요구사항 기반으로 다시 만듭니다. 다음 내용들은 지시 예시.

- 한 번에 하나의 기능만 요청
- 코드를 쓰기 전에 **계획을 먼저 말하게 하고 검토**한 뒤 진행
- 기능 단위로 커밋
- **사소한 변화와 문제점들을 잘 기록해서 성찰기를 완성하시기 바랍니다.**

### Phase 4 — 성찰기 작성

- 성찰기 완성 및 발표 준비
- **널리 알려진 Tip이나 Claude Code만의 Tip보다 작아도 차별적이고 범용적인 Tip이나 본인의 응용만의 Tip 등이 득표에 유리하도록 투표 가이드 할 예정입니다.**

## 6. 발표

- 1인 7분 + 질의 3~5분
- 구성 권장: 데모 2분 → 나이브 베이스라인 1분 → **문제 사례와 대응 3.5분** → 결론 0.5분
- **발표 시간의 절반 이상을 문제 사례와 대응에 쓰세요.** 데모 자랑에 시간을 쓰면 성찰 트랙 득표가 나오지 않습니다.
- 코드 전문을 띄우고 읽지 마세요. **전/후 비교**가 보이게 하세요.

- 투표는 순위 구간 방식으로 점수 환산될 예정입니다 (0표자가 0점이 되는 것 방지)

### 투표 폼 예시

- **실용성 트랙**: *"이번 학기 안에 내가 실제로 한 번이라도 쓸 것 같은 결과물 4개를 고르세요"*
- **본인 투표 차단, 친목 투표 금지, 합당한 투표 사유 작성 예정**

## 8. 자주 나오는 질문

**결과물이 미완성이면 큰 감점인가요?**
완성도 항목(20%)에서 감점됩니다. 하지만 미완성 원인을 정확히 진단한 성찰기는 나머지 60%에서 충분히 회수할 수 있습니다.

**코드를 한 줄도 직접 안 써도 되나요?**
됩니다. 다만 **읽지 않는 것은 허용되지 않습니다.** 발표 질의에서 "이 부분은 왜 이렇게 동작하나요"에 답하지 못하면 감점됩니다.

**Claude Code 외의 도구를 써도 되나요?**
주 도구는 Claude Code여야 합니다. 병행했다면 성찰기에 명시하고 비교 관찰을 적으면 좋은 소재가 됩니다.

**Phase 0에서 만든 게 생각보다 잘 나왔는데요?**
그것도 좋은 발견입니다. **어떤 종류의 요구사항에서 나이브한 접근이 통했는지**를 분석하세요. 다만 그 결과물을 그대로 제출하지는 마세요.

**주제가 다른 사람과 겹치면요?**
겹쳐도 됩니다. 같은 주제를 다르게 접근한 사례는 오히려 좋은 비교 소재입니다.
